# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A monorepo for **The Next Protein Nepal**, a plant-based meat brand, with three apps:

- **`frontend/`** — the public marketing/catalogue site (React SPA) with a real product catalogue, cart, and checkout (eSewa/Stripe/COD payments).
- **`admin/`** — an internal admin app for managing products, tracking orders, and reading contact-form enquiries.
- **`backend/`** — a Flask + SQLAlchemy API shared by both frontends (SQLite locally, swappable to Postgres via `DATABASE_URL`).

The original site (still the basis for `frontend/`'s design and copy) was scaffolded via **Figma Make** and had no backend, cart, or checkout at all — see `frontend/src/imports/pasted_text/next-protein-nepal-website.md` for that original brief if you need brand/content background. The backend, cart/checkout, and `admin/` app were added later and are not part of the original Figma Make project.

## Commands

```bash
# frontend (public site) - http://localhost:8443
cd frontend && npm install && npm run dev
npm run build    # production build to frontend/dist/
npm run format   # oxfmt

# admin app - http://localhost:8443/admin (via the frontend's dev proxy) or http://localhost:5174/admin directly
cd admin && npm install && npm run dev
npm run build    # production build to admin/dist/

# backend API - http://localhost:5000
cd backend && python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # see "Payment gateways" below before relying on Stripe
flask db upgrade               # apply migrations (creates backend/instance/app.db)
flask seed-admin --email you@example.com --password ... --name "Admin"
flask seed-products            # inserts the real "Protein Loaf" product
flask run --port 5000
```

Neither `frontend/` nor `admin/` has a lint or test script — don't assume `npm test`/`npm run lint` exist. The backend has no test suite either; verify changes by running the app and hitting endpoints directly (`curl`, or the frontend/admin UI against a local `flask run`).

## Architecture

### Backend (`backend/`)

- Flask app-factory pattern: `app/__init__.py` (`create_app`) wires up SQLAlchemy, Flask-Migrate, Flask-JWT-Extended, and Flask-CORS, then registers blueprints from `app/api/`.
- **Models** (`app/models/`): `Product` → has many `ProductVariant` (pack sizes/prices, e.g. "500g retail" vs "1kg enquiry-only") and `ProductImage`. `Order` → has many `OrderItem`. `AdminUser` for admin auth (no public signup — created only via `flask seed-admin`). `Enquiry` for Contact-form submissions (`status`: `new`/`read`/`responded` — viewing one via `GET /api/admin/enquiries/<id>` auto-marks it `read`, like an inbox).
- **Order integrity**: `OrderItem` *snapshots* `product_name_snapshot`/`variant_label_snapshot`/`unit_price_npr` onto the row at order time (rather than only joining live via FK), so historic orders stay accurate even if a product is later edited or deleted. Prices are always taken from the server-side `ProductVariant.price_npr` in `app/api/orders.py::create_order` — never trust a client-sent price.
- **Payment methods**: `esewa`, `stripe`, or `cod` (Cash on Delivery) exist in the code, but only **`cod` is currently enabled** (`ENABLED_PAYMENT_METHODS` in `app/config.py`, env-configurable, defaults to `cod` only) — eSewa/Stripe are fully built and tested but switched off for initial launch, to re-enable later. This one config value gates both order creation (`orders.py::create_order`) *and* the payment initiate endpoints directly (`payments.py::_require_enabled`), so a disabled method can't be reached even by calling the API directly, bypassing the checkout UI. To re-enable: set `ENABLED_PAYMENT_METHODS=cod,esewa,stripe` (or whichever subset) in `backend/.env`, **and** add the methods back to `frontend/src/pages/Checkout.tsx`'s `ENABLED_METHODS` array (that array only controls which buttons render — the backend config is the real gate). COD orders skip `pending_payment` entirely and go straight to `processing` (there's no gateway callback to wait on); `payment_status` stays `unpaid` until an admin manually marks it `paid` via `PATCH /api/admin/orders/<id>/status` (that endpoint accepts `status` and/or `payment_status` independently — the only path to flip payment_status for COD, since there's no gateway to verify against).
- **Phone validation**: both `Checkout.tsx` (client-side) and `orders.py::create_order` (server-side, authoritative) require a customer phone with at least 10 digits, or exactly 7 (a bare landline number) — see `_is_valid_phone` in `orders.py` / `isValidPhone` in `Checkout.tsx`. Keep these two in sync if the rule changes.
- **API surface**: public endpoints live in `app/api/products.py`, `orders.py`, `payments.py`, `enquiries.py`; everything under `/api/admin/*` (`admin_auth.py`, `admin_products.py`, `admin_orders.py`, `admin_dashboard.py`, `admin_enquiries.py`) requires a JWT (`@jwt_required()`) obtained via `POST /api/admin/login`.
- **Payments** (`app/services/esewa.py`, `stripe_gateway.py`): both gateways are redirect-based — the backend signs/initiates server-side (eSewa: signed form fields; Stripe: a hosted Checkout Session), the browser is redirected to the gateway, and the gateway redirects back to a frontend `/payment/{esewa,stripe}/return` page. Critically, the callback query params are **never trusted directly** — `app/api/payments.py` always re-verifies server-side (eSewa's status-check API, Stripe's Checkout Session retrieval) before flipping an order to `paid`. Module is named `stripe_gateway.py`, not `stripe.py`, to avoid any ambiguity with the installed `stripe` package it imports.
- **Uploads**: admin-uploaded product images go to `backend/uploads/` (gitignored, served via a Flask static route registered in `admin_products.py`). This is distinct from `backend/app/static/seed/`, which holds the *tracked* seed images used by `flask seed-products` — don't confuse the two.
- **Database**: SQLite by default at an absolute path under `backend/instance/` (see `app/config.py` — deliberately absolute, not `sqlite:///instance/app.db`, because a relative sqlite URI resolves against the process's CWD and silently fails depending on where `flask` is invoked from). Set `DATABASE_URL` to point at Postgres in production.

### Frontend (`frontend/`)

- Same structure as the original Figma Make site (`src/pages/`, `src/components/`, routing in `App.tsx`) — see below for what changed.
- **`src/lib/api.ts`** is the only place that talks to the backend (reads `VITE_API_BASE_URL`). Product data no longer lives in the page components — `Products.tsx`, `ProductDetail.tsx`, and `Home.tsx`'s featured-product section all fetch from the API rather than hardcoding a single product.
- **Routing**: `/products/:slug` is a real dynamic route (`ProductDetail.tsx` uses `useParams`) — it replaced a hardcoded static `/products/protein-loaf` route.
- **Cart**: `src/context/CartContext.tsx`, a React Context + `useReducer` persisted to `localStorage`, wraps the app in `main.tsx`. `Header.tsx` shows a live cart badge via `useCart()`.
- **Checkout flow**: `Cart.tsx` → `Checkout.tsx` (`POST /api/orders`, then initiates the chosen gateway and redirects, or for COD skips straight to order confirmation) → gateway's hosted payment page → `PaymentReturn.tsx` at `/payment/esewa/return` or `/payment/stripe/return` (confirms the final order/payment status with the backend) → `OrderStatus.tsx` at `/order/:orderNumber` for later lookups (requires the order's phone number as a light anti-enumeration guard, matching the backend's `GET /api/orders/<order_number>?phone=`).
- A product's "enquiry-only" variant (e.g. wholesale packs with no fixed price) is excluded from Add-to-Cart — it keeps the original WhatsApp-enquiry / `/wholesale` contact flow instead of checkout.
- **`Contact.tsx` and `Wholesale.tsx` both submit for real** (`POST /api/enquiries`) and show up in the admin app's Enquiries section. There's one shared `Enquiry` model/table for both — `Wholesale.tsx` maps its business-specific fields (`businessName`→`org`, `contactPerson`→`name`, `businessEmail`→`email`, `businessType`→`subject`, `enquiry_type` fixed to `'Wholesale Enquiry'`) and folds the rest (address/city/monthly requirement/pack size/intended use) into the `message` body as labeled lines, rather than adding dedicated columns for them.
- **Styling/assets/path-alias conventions are unchanged** from before the monorepo split — Tailwind v4 via `@theme inline` in `src/index.css`, `assets/` for images, `@/*` → `src/*`.

### Admin (`admin/`)

- Independent Vite + React + TS + Tailwind app (own `package.json`, dev port `5174`), not part of the Figma Make project — no `.figma/` plugins here.
- **Lives at `/admin`, not its own domain/port**, so the public site and admin read as one product to visitors. This is baked into the app two ways: `vite.config.ts` sets `base: '/admin/'` (so built asset URLs are `/admin/assets/...`) and `App.tsx`'s `BrowserRouter` sets `basename="/admin"` (so its own routes like `/orders/5` resolve as `/admin/orders/5`). In dev, `frontend/vite.config.ts` proxies `/admin/*` (including the `@vite/client` WS connection) to the admin dev server on `5174`, so `http://localhost:8443/admin` works from the same origin as the public site without touching anything in `frontend/`'s own code. Direct access via `http://localhost:5174/admin` still works too (note: `http://localhost:5174/` alone now 404s — the app only serves under `/admin` because of `base`).
- **Production routing is wired up** (merged single-deployment approach): `frontend/package.json`'s `build` script now does more than `vite build` — it also installs and builds `admin/` (`npm --prefix ../admin install && npm --prefix ../admin run build`) and copies `admin/dist/` into `frontend/dist/admin/`. `frontend/vercel.json`'s rewrites list `/admin/(.*) -> /admin/index.html` **before** the general `/(.*) -> /index.html` catch-all (rewrite order matters — Vercel uses first-match-wins, so the admin rule would never fire if it came second). Real static files (JS/CSS under `/admin/assets/...`) are served directly by Vercel without hitting any rewrite; only client-side-routed pages like `/admin/orders/5` need the fallback. Verified locally end-to-end (full build + a static file server) before trusting this in production — Vercel's actual rewrite engine still can't be tested without a live deploy, so if `/admin` 404s or shows the wrong app after deploying, check this file first. `admin/vercel.json` (a separate-deployment SPA fallback) is now unused dead weight under this architecture — harmless, kept only in case you ever split admin into its own Vercel project instead.
- `src/index.css` copies the frontend's `@theme inline` token block verbatim for visual consistency; keep the two in sync manually if brand colors change.
- **Auth**: `src/context/AuthContext.tsx` + `src/lib/api.ts` store the JWT in `localStorage`; `ProtectedRoute.tsx` redirects to `/login` when there's no valid token, and the API client's `request()` helper redirects to `/login` on any `401`.
- **Product form** (`src/pages/products/ProductForm.tsx`): the free-text "Details" fields (ingredients, nutrition facts, cooking stats, storage info, FAQs) use small plain-text formats (documented in each field's placeholder, e.g. `"Label: Value"` per line) that get parsed into the JSON shape the backend expects — there's no nested dynamic-field UI for these, by design, to keep the form simple.
- Image upload only works once a product exists (`isEdit`) — creating a new product redirects straight to its edit page so images can be attached.
- **Enquiries** (`src/pages/enquiries/`): read-only inbox for Contact-form submissions, with a status dropdown (`new`/`read`/`responded`) and an unread-count badge in `Layout.tsx`'s nav (re-fetched on every route change) and on the Dashboard.

## Payment gateways (eSewa / Stripe / COD)

**Only COD is currently enabled** (see the "Payment methods" note above — `ENABLED_PAYMENT_METHODS` in `backend/.env`). Everything below describes the eSewa/Stripe integrations as fully built and tested — they're just switched off at launch, not missing.

- **eSewa**: uses the publicly documented UAT test merchant code (`EPAYTEST`) and secret key (`8gBm/:&EnhH.1/q` — exact string, no trailing punctuation; verified against the raw HTML of `developer.esewa.com.np/pages/Test-credentials`, since an earlier AI-summarized fetch had silently appended a stray `(` that broke every signature for a while) — works out of the box, no signup needed for development. To manually click through a sandbox payment in a browser, log in on eSewa's hosted page with eSewa ID `9711111111`/`...112`/`...113`, password `Test@123`, MPIN `1122`, OTP token `123456` — these change occasionally; re-verify against the **raw page source** (not just a fetched summary) at `developer.esewa.com.np/pages/Test-credentials` if login or signing fails, since exact-string secrets are easy for a summarizer to corrupt. eSewa's docs (`developer.esewa.com.np/pages/Epay`) are the authoritative source for the ePay v2 URLs/fields we implemented; they also document a newer, separately-designed **"Intent" API** (deeplink/booking-based, different signature scheme) marked as their current recommendation — we deliberately stayed on ePay v2 (still fully documented/supported) rather than doing an unprompted migration; worth a conscious decision later, not a silent swap. Before going live, get real merchant credentials from `merchant.esewa.com.np` and swap **both** `ESEWA_INITIATE_URL` and `ESEWA_STATUS_URL` from their `rc-epay`/`rc` sandbox hosts to the production hosts documented in `backend/.env.example` — not just the merchant code/secret.
- **Stripe** (`app/services/stripe_gateway.py`): uses Stripe's hosted Checkout (redirect-based, same pattern as eSewa) — the backend creates a Checkout Session server-side and hands the frontend a `url` to redirect to; on return, `app/api/payments.py::stripe_callback` re-retrieves the session from Stripe's API (never trusts the `session_id` alone) and checks `payment_status == 'paid'`. Charges in NPR directly — NPR is a supported 2-decimal Stripe presentment currency, so no currency conversion. Like Khalti before it, there's **no shared public test key**: `STRIPE_SECRET_KEY` is blank by default and payment initiation fails with a clear error until you sign up free at `dashboard.stripe.com/register` and paste a test secret key (`sk_test_...`, from `dashboard.stripe.com/test/apikeys`) into `backend/.env` — test mode needs no business verification and works from any country. **Important for going live**: Stripe does not support Nepal-registered businesses for direct payouts — a Nepal-based business needs a registered entity in a Stripe-supported country (e.g. Singapore, India, US, UK — see Stripe's country list) to receive real money, or must route through that entity. This is a business decision outside this repo, not something fixable in code; test mode is unaffected and works today regardless.
- **COD** (Cash on Delivery): no gateway at all — see the "Payment methods" note above.

There is no Khalti integration anymore (removed in favor of Stripe) — if old notes/links reference `KHALTI_*` env vars or `/payment/khalti/return`, they're stale.

## Security (pre-deployment checklist)

A full security pass has been done; here's what's in place and what still needs a human decision before going live:

- **Boot-time secret check**: `app/__init__.py::_refuse_insecure_production_secrets` makes the app **refuse to start** if `APP_ENV=production` and `SECRET_KEY`/`JWT_SECRET_KEY` are still their dev-default values — this is the main guardrail against accidentally deploying with forgeable JWTs. Set `APP_ENV=production` plus real random secrets (`python3 -c "import secrets; print(secrets.token_hex(32))"`) on any real deployment; local dev is unaffected (`APP_ENV` defaults to `development`).
- **`wsgi.py`'s `debug=` flag** is now tied to `APP_ENV` too (was hardcoded `True`, which is remote-code-execution-via-Werkzeug-debugger if ever reachable from the internet).
- **Rate limiting** (Flask-Limiter, `app/extensions.py`): `POST /api/admin/login` (5/min — brute-force guard), `POST /api/orders` and both `/api/payments/{esewa,stripe}/initiate` (10/min), `POST /api/enquiries` (5/min). Storage is in-process memory by default (`RATELIMIT_STORAGE_URI`) — fine for a single worker process; multiple gunicorn workers in production need a shared backend (Redis) or each worker enforces its own separate limit.
- **Stock-exhaustion fix** (`app/services/order_maintenance.py::release_stale_pending_orders`): `create_order` reserves stock immediately (to prevent overselling), which used to mean an abandoned/spammed checkout could lock stock away forever — there's no task scheduler in this stack to expire them. This now runs opportunistically before any stock-sensitive operation (new order creation, payment initiation) and cancels+restores stock for anything stuck in `pending_payment` past `STALE_ORDER_MINUTES` (30 min default) — self-healing without needing cron/Celery/Redis. Combined with the rate limit above, this bounds both how much stock a spam burst can lock up and for how long.
- **Security headers**: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` set on every response via an `after_request` hook in `app/__init__.py`.
- **Upload validation** (`app/services/uploads.py`) now checks actual file *content* (magic bytes) against the claimed extension, not just the filename — a `.png`-named file that isn't really a PNG is rejected.
- **`flask seed-admin`** now refuses passwords under 10 characters (this account has full admin access, no granular roles), and reads `ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_NAME` from the environment (`.env` locally, your deploy platform's secret store in production) when CLI flags aren't passed — so `flask seed-admin` alone (no arguments) does the right thing, and the password never has to be typed as a literal CLI argument (shell history, process list). Safe to re-run any time — updates the existing admin's password/name rather than duplicating.
- **Dependency audit**: `pip-audit` and `npm audit` were run and all findings fixed (Flask/Werkzeug/requests/python-dotenv bumped to patched versions in `backend/requirements.txt`; `react-router`/`react-router-dom` updated in `frontend/`). Re-run both before each future deploy — new CVEs get published continuously and this snapshot will go stale.
- **HSTS**: `Strict-Transport-Security` added to the backend's `after_request` hook, and separately as a Vercel response header in both `frontend/vercel.json` and `admin/vercel.json` (browsers ignore it entirely over plain HTTP, so it's inert until the deployment is actually HTTPS).
- **CSP (Content-Security-Policy)**: added via `headers` in `frontend/vercel.json` and `admin/vercel.json` (this is hosting-layer, not something Flask can set for a static SPA deploy). `script-src 'self'` with no `'unsafe-inline'`/`'unsafe-eval'` — the main real protection, confirmed safe today (no inline `<script>`s, no `dangerouslySetInnerHTML`/`eval` anywhere). Two things to know if you touch this: (1) `frontend`'s `style-src` needs `'unsafe-inline'` because the app uses JSX `style={{...}}` inline styles extensively (`admin` doesn't, so its CSP is stricter there); (2) `frontend`'s `form-action` explicitly allowlists `rc-epay.esewa.com.np`/`epay.esewa.com.np` because `Checkout.tsx`'s `redirectToEsewa()` does a real cross-origin form POST to eSewa — a naive `form-action 'self'` would silently break eSewa checkout. `connect-src`/`img-src` are left as `https:` (broad) rather than pinned to the backend's exact domain, since that domain isn't known yet at authoring time — tighten these once the backend's production URL is fixed. If you ever enable Google Analytics or custom scripts via `.figma/make/site.json` (currently unset), note `vite.config.ts` injects those as **inline** `<script>` tags, which this CSP's `script-src 'self'` will block — you'd need to add `'unsafe-inline'`/a nonce or load them as external `<script src>` instead.
- **JWT revocation** (`RevokedToken` model, `app/api/admin_auth.py::logout`): logging out now actually invalidates the token server-side (added to a blocklist checked via `@jwt.token_in_blocklist_loader` in `app/__init__.py`), not just a client-side `localStorage` clear — previously a stolen token stayed valid for its full lifetime with no way to cut it off. Access tokens expire in 15 minutes regardless (Flask-JWT-Extended default, not explicitly configured) — the blocklist entry's own `expires_at` is opportunistically pruned on each logout call once its underlying token would've expired anyway, so this table stays small without needing a cron job.
- **Admin audit log** (`AdminAuditLog` model, `app/services/audit.py::log_admin_action`, viewable at `admin/audit-log` in the admin app): every product create/update/delete/image-upload/image-delete, order status/payment-status change, and enquiry status change is now recorded with who did it and when. Viewing an enquiry (which auto-marks it read) is deliberately **not** logged — that's an implicit side effect of reading, not a deliberate action worth an audit trail entry. `log_admin_action()` only adds to the current DB session (doesn't commit) so it lands atomically in the same transaction as the change it's describing — always call it before the route's own `db.session.commit()`.

**Known, accepted risks — not fixed, by design or because they need a decision I can't make:**
- **No CAPTCHA** on the public Contact/Wholesale/checkout forms — needs a third-party provider (hCaptcha/reCAPTCHA) and API keys, which requires a signup decision outside this repo. Rate limiting above is the current mitigation.
- **Admin JWT lives in `localStorage`** (`admin/src/lib/api.ts`), not an httpOnly cookie — readable by any JS on the page if an XSS bug is ever introduced (none currently found — no `dangerouslySetInnerHTML`/`eval` anywhere in either frontend). Switching to cookie-based auth is a real architecture change (CSRF handling, cross-port cookie config in dev) that hasn't been done.
- **Public order lookup** (`GET /api/orders/<order_number>?phone=`) is a light deterrent (phone-match), not strong auth — acceptable at this scale, not airtight against a targeted guess.
- **Seeded/test credentials** used throughout local dev (admin password, sandbox payment credentials) must be rotated before any production use — none of them live in git, but they've been used in this conversation's history. The local admin password has already been rotated once (via `ADMIN_PASSWORD` in `backend/.env`) for this reason — rotate again before any real deployment, since this local one has also now been typed in a conversation transcript.

## Known repo quirks

- There was originally **no `.gitignore`** (only an ineffective, dotless file named `gitignore`), so `node_modules/`/`dist/` used to be committed. This has been fixed with a proper root `.gitignore` covering all three apps' `node_modules/`/`dist/`/build artifacts plus Python's `venv/`/`__pycache__/`/`instance/`. Still, double-check `git status` before any broad `git add`.
- **Vercel deploy**: the frontend used to be deployed from the repo root; after the monorepo restructure, Vercel's project "Root Directory" setting needs to point at `frontend/` (a dashboard change, not something fixable from the repo).
